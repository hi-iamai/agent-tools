# Agent 底层 Tool 扩展评测：阶段结果

> 日期：2026-07-29  
> 状态：阶段性数据，不是最终全景报告

## 1. 本阶段覆盖范围

在原 Tool Surface Pilot 之外，已补充：

- 文件发现：`rg --files`、`git ls-files`、Python `rglob/scandir`；
- 文本搜索：`rg`、`git grep`、Python `re`、SQLite FTS5；
- Linux runner 候选：GNU `find/grep`、`fd`、`ugrep`、`ag`；
- WebFetch Client：requests、HTTPX、aiohttp、curl、wget；
- HTML 处理：Raw、BeautifulSoup、lxml、Readability、Trafilatura、Selectolax；
- 浏览器渲染：Playwright Core + Edge；
- API Fetch：JSON、gzip、redirect、500、分页、429、并发；
- 运行形态消融：每次新建 Client 与持久 Session/连接池。

本地网页和 API fixture 具有固定 ground truth，可避免公网内容变化污染结果。

## 2. Windows 搜索阶段数据

### 2.1 文件发现

| Backend | 中位时延 | 平均 Recall | 平均 Precision | 说明 |
|---|---:|---:|---:|---|
| `rg --files` | 43.8ms | 99.99% | 98.52% | 默认 ignore 语义与全量 oracle 有少量差异 |
| `git ls-files` | 60.4ms | 100% | 100% | 当前固定仓库全部相关文件被跟踪 |
| Python `os.scandir` | 533.0ms | 100% | 100% | 进程内、全量遍历 |
| Python `Path.rglob` | 915.0ms | 100% | 100% | 最慢的无索引实现 |

Windows `find.exe` 不是 GNU find，命令语义不兼容，因此结果记录为不可用，而不是
把失败时延当作性能数据。

### 2.2 文本搜索

| Backend | 中位时延 | 平均 Recall | 平均 Precision |
|---|---:|---:|---:|
| SQLite FTS5 | **1.44ms** | 99.997% | 99.39% |
| `git grep` | 137.6ms | 100% | 100% |
| `ripgrep` | 165.4ms | 99.998% | 100% |
| Python `re` 全量扫描 | 1414.9ms | 100% | 100% |

FTS5 的查询速度不能脱离索引成本解读：

```text
索引构建：4.06s
索引大小：135.0MB
索引文件：5,695
索引行数：1,111,100
```

按本轮中位数粗略计算：

- 相比 `git grep`，每次 literal query 节约约 136ms；
- 只考虑一次构建成本，约需要 30 次查询才能摊平；
- 这还没有包含增量维护、陈旧结果和磁盘成本；
- FTS5 不能直接替代通用 regex/结构搜索。

因此索引方案必须以查询密度和生命周期为自变量，而不是只报 warm query。

### 2.3 WSL1 对照

已使用修正后的同一 runner 分别复跑：

- `wsl_ntfs`：Ubuntu 24.04 WSL1 访问 `/mnt/e`；
- `wsl_ext4`：仓库副本位于 WSL Linux 根文件系统。

部分中位时延：

| Backend | WSL NTFS | WSL Linux FS |
|---|---:|---:|
| `git ls-files` | 9.5ms | 10.7ms |
| `fd` | 87.3ms | 103.0ms |
| `rg --files` | 87.5ms | 103.7ms |
| GNU `find` | 140.5ms | 152.6ms |
| `git grep` | 约 186ms | 约 343ms |
| ripgrep | 约 287ms | 约 460ms |
| ugrep | 约 448ms | 约 775ms |
| `ag` | 约 611ms | 约 774ms |
| GNU grep | 约 769ms | 约 1813ms |

这不是原生 Linux 结论。当前机器是 WSL1，Linux 根文件系统也仍受 WSL1 系统调用实现
影响。本轮还观察到 `/mnt/e` 在部分 CLI workload 上反而快于 WSL Linux FS，因此不能使用
“ext4 一定更快”的先验替代实际测量。

`fd` 和 GNU find 的 Precision 低于 oracle，主要来自 ignore/隐藏文件和路径语义差异；
这正是文件 Tool 评测必须同时报告速度和覆盖语义的原因。

### 3.2 Client 与抽取组合

在本地固定 fixture 中：

| 组合 | 平均证据 Recall | 平均正文 F1 | 中位总时延 |
|---|---:|---:|---:|
| aiohttp + Raw | 85.7% | 29.5% | 1.93ms |
| aiohttp + lxml text | 85.7% | 47.7% | 2.02ms |
| requests Session + lxml | 85.7% | 47.7% | 11.47ms |
| HTTPX persistent + lxml | 85.7% | 47.7% | 11.97ms |
| Playwright + Edge rendered text | **100%** | **55.6%** | **540.70ms** |

动态页面已经改为通过独立 API 在 JavaScript 执行后加载答案，原始 HTML 不包含答案。
因此所有纯 HTTP Client/Extractor 在动态页证据 Recall 均为 0，Playwright 为 100%。
正文 F1 同时衡量正文保留和导航、footer、脚本、重复文本等噪声。

不同正文抽取器表现：

- lxml、BS4、Selectolax、Trafilatura 在静态页面保留主要证据，但无法读取动态 API 内容；
- Readability 对短页面、表格和代码片段存在额外丢失；
- 丢失主要发生在动态正文：HTTP 抓到的是脚本，不是执行后的 DOM。

Playwright 对所有页面包括动态页都达到 100% recall，但中位时延约为 aiohttp/raw 的
280 倍。因此当前数据支持 **Fetch Waterfall** 的研究价值：

```text
HTTP fetch
→ 轻量 HTML text/extractor
→ 证据不足或检测到动态壳时
→ Browser render
```

它还不支持“固定使用某一个抽取器”的最终结论。

Windows 上 `wget` 命令解析到了不可用/非预期实现，本轮记为环境不可用；WSL 中的 GNU
wget 应单独报告。

## 4. 结构搜索阶段数据

以 Python AST 的精确节点位置作为 oracle：

| Backend | 平均 Precision | 平均 Recall | 中位时延 | 中位原始输出 |
|---|---:|---:|---:|---:|
| Python AST 全仓解析 | 100% | 100% | 4031.9ms | 11.8KB |
| ast-grep | 93.4% | 97.8% | 641.3ms | 处理后结果较小；原始 JSON 中位约 699KB |
| ripgrep 结构 regex | 78.5% | 73.3% | **89.7ms** | 24.2KB |

结构任务已经从 3 个扩展到 15 个，包含 decorator、调用、yield、try/except、with、
async with、raise、lambda 和 named expression。这组数据说明：

- regex 候选搜索快，但对于语法结构不能保证完整召回；
- ast-grep 在结构语义上接近 AST oracle，速度显著优于纯 Python 全仓解析；
- ast-grep 的默认 JSON 输出非常大，Adapter 必须裁剪字段；
- Python AST 适合作为 ground truth 和可编程分析基础，但每次全仓冷解析不适合作为高频 Tool；
- AST 缓存和增量解析值得继续验证。

## 5. API Fetch 阶段数据

### 4.1 分页

三页、九条记录的固定 API：

| Client/形态 | 中位耗时 | 正确率 |
|---|---:|---:|
| requests Session | **5.28ms** | 100% |
| aiohttp（当前每任务 Session） | 5.44ms | 100% |
| HTTPX persistent Client | 13.53ms | 100% |
| requests 每次新连接 | 28.27ms | 100% |
| curl 子进程 | 77.83ms | 100% |
| HTTPX 每次新建 Client | 502.60ms | 100% |

结果明确说明：**运行形态可能比 HTTP 库品牌本身更重要。**

HTTPX 每次创建 Client 的结果很差，但持久 Client 后从约 503ms 降到 13.5ms。因此不能用
“每次新建 Client”数据宣称 HTTPX 本身慢。

### 4.2 并发 8、共 16 请求

| Client/形态 | 中位吞吐量 |
|---|---:|
| HTTPX persistent Client | **1107.8 req/s** |
| requests Session | 835.5 req/s |
| aiohttp | 588.4 req/s |
| requests 每次连接 | 343.3 req/s |
| curl 子进程 | 52.5 req/s |
| HTTPX 每次新建 Client | 17.4 req/s |

加入原生异步实现后，Windows loopback 中 aiohttp `gather` 约为 1561 req/s，
HTTPX AsyncClient 约为 96 req/s。同步线程池、异步事件循环和子进程并发需要分别报告。

这些是 loopback fixture 数据，只用于隔离 Client 初始化、连接池和子进程开销，不能外推
到公网吞吐。

### 4.3 异常

测试已覆盖：

- 302 redirect；
- gzip；
- HTTP 500；
- 独立的 429 重试；
- 分页聚合。

429 fixture 已按 `environment/client/repeat` 隔离，每个可用 Client 必须独立经历两次
429 后再成功。客户端仍需要由 Tool Adapter 实现统一的状态码语义、重试、`Retry-After`、最大页数和
幂等性策略。HTTP 库本身不会自动提供完整 Agent 级策略。

## 7. 运行形态、索引生命周期与基础 I/O

### 7.1 运行形态

同一个无索引 Python 全仓 literal scanner：

| 运行形态 | 中位时延 |
|---|---:|
| 每次启动 ripgrep | 144.0ms |
| 持久 Python STDIO worker | 761.4ms |
| 持久 Python HTTP daemon | 777.4ms |
| 每次启动 Python scanner | 843.9ms |

持久进程仅消除了约 70～80ms 的 Python 启动开销，扫描算法本身仍是主成本。这说明运行形态
优化不能代替更好的 Engine；MCP/daemon 的协议开销需要和 Engine 成本分开测量。

### 7.2 SQLite FTS5 生命周期

在临时完整仓库副本上：

```text
首次构建：37.7s
新增文件并可查询：286ms
更新文件并移除旧结果：225ms
删除文件并移除结果：214ms
数据库重开并查询：151ms
```

首次构建比之前直接工作区测试慢，说明文件复制位置、缓存状态和杀毒/文件系统环境会显著
影响索引成本。最终报告必须同时提供 warm/cold 和存储位置，而不能只使用一个 build 数字。

## 8. 阶段性观察

现阶段数据已经推翻“只要比较 rg 就够了”的做法：

- 索引 warm query 可比无索引扫描快两个数量级，但有明显构建与空间成本；
- 文件发现的 ignore/tracked 语义会改变 Precision/Recall；
- WebFetch 的 HTTP Client、正文抽取和浏览器渲染是三个独立变量；
- 动态页面使轻量 extractor 系统性丢失证据；
- HTTP Client 是否持久复用，对结果的影响可超过具体库之间的差异；
- 子进程 CLI 在单次调用中尚可，但高并发和多页 API 中开销明显。

因此最终报告应按 Tool 类型分别给出数据和 Pareto 前沿，而不是提前组合成一个默认方案。
