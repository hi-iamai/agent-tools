# 严格运行形态与协议开销实验

> 环境：Ubuntu 24.04 WSL1  
> Engine：同一 Python 预加载内存 Corpus、同一 literal scan 函数  
> Schema：`strict-runtime-v1`  
> 原始数据：`benchmark/results/extended/strict_runtime_*`

## 1. 实验控制

所有 Adapter 共享：

- 4,096 条预加载记录；
- 相同 `needle-common` 查询；
- 相同结果顺序；
- 相同 `limit`；
- 相同 JSON 字段；
- 相同四档 payload：约 1KB、10KB、100KB、1MB；
- 每档 20 次；
- 并发 1/4/8/16；
- 吞吐测试每点 64 请求。

比较：

- 同进程同步 Engine-only；
- 同进程同步 + JSON；
- 同进程 `async def`；
- 持久 event loop async；
- `asyncio.to_thread`；
- ProcessPool；
- 每次启动进程；
- 持久 JSONL STDIO；
- 持久 HTTP；
- MCP STDIO；
- MCP Streamable HTTP。

## 3. 吞吐

并发 8、64 请求、约 10KB 响应：

| Adapter | 吞吐 |
|---|---:|
| ProcessPool | 5,083 req/s |
| Direct sync + threads | 3,216 req/s |
| Persistent async loop | 2,683 req/s |
| Persistent STDIO | 1,628 req/s |
| MCP STDIO（串行） | 855 req/s |
| MCP HTTP | 573 req/s |
| Persistent HTTP | 167 req/s |
| Per-call process | 31 req/s |

CPU-bound Python Engine 受 GIL 影响，线程并发没有线性增长；ProcessPool 在并发 16 时达到
约 4,170 req/s。STDIO 本质串行，传入更高“并发”只会在客户端排队。

## 5. 故障、取消与恢复

| Case | 结果 | 观察 |
|---|---|---|
| HTTP 100ms timeout | 通过 | Client 在约 101ms 返回超时 |
| timeout 后下一请求 | 通过 | Server 仍健康 |
| cooperative thread cancel | 通过 | 约 104ms 停止 |
| ProcessPool 已运行任务 cancel | 预期不可取消 | 仍运行约 1.02s |
| HTTP server crash + restart | 通过 | 约 159ms 恢复 |
| STDIO worker kill + restart | 通过 | 重启后约 102ms 可服务 |

## 6. 结论

1. **同进程同步函数是最小开销基线。**
2. 对纯 CPU 同步 Engine，写成 `async def` 不会自动加速；每次 `asyncio.run` 反而增加开销。
3. 持久 event loop 的 async 包装成本较低，但仍高于同步直接调用。
4. `asyncio.to_thread` 对亚毫秒任务开销明显，仅适合避免阻塞或处理更长任务。
5. ProcessPool 单调用成本高，但 CPU-bound 并发吞吐最好。
6. 持久 STDIO 的单调用成本接近 direct async，明显优于每次启动进程。
7. 每次启动进程是短任务中最大的固定成本。
8. MCP STDIO/HTTP 在小 payload 下是毫秒级开销；大 payload 下结构包装与序列化成为主要成本。
9. 普通本地 HTTP 在本次 WSL1 中尾延迟不稳定，必须报告 P95。
10. 取消能力取决于 Engine 是否协作；协议本身不能强制停止已运行的 CPU 任务。
